# Spec: Disabled features and the unported-feature catalog

> **WARNING**: Never trust docs/logs without fully auditing code. Always verify against actual implementation.
Status: updated 2026-11-05 (user directive). Governs every feature this build turns off
and every capability that is intentionally not ported yet.
Related: `specs/rust-backend-replacement.md`,
`specs/workflow-capability-boundary.md`, `specs/typescript-frontend-only.md`.

## 1. Product rule (why anything is disabled)

- The app stays **fully provider-agnostic and open source**: any OpenAI/Anthropic-compatible provider, API key or
  custom endpoint keeps working exactly as before. Nothing here removes a provider.
- **No connections to zcode infrastructure are made.** All ZCode services (auth, quota, cloud sending data) have been removed.
  - No sign-in / token claim / Z.ai OAuth
  - No free-credit claim / billing/balance reads
  - No account setup through ZCode services
  - No remote feature flags, remote content catalogs, remote scheduling, remote sync, remote usage, telemetry, share, feedback
- Everything that talked to zcode infrastructure is **disabled/removed**. Disabled means: the call is never made, and the feature answers a documented
  local state or a named error. It is never a silent success.
- "Disabled" is not the same as "unimplemented": the disabled surface is tested and listed
  here; the unimplemented surface is listed in §4 and must not be presented as done.

## 3. Case-2 decisions: what we deliberately do not build, why, and the better alternative

> Rule (user directive): if something cannot be produced first, record concrete reasoning
> and name a better alternative; if building it would harm, record that too.

### 3.1 Off-peak scheduling — disabled, not ported to the cloud

- **Why not built:** the scheduler _is_ a zcode cloud service (ticket allocation, promotion,
  settlement). There is no local or third-party equivalent to talk to, and the user policy
  forbids that connection. Porting the client while refusing the server would produce a
  feature that can never run — a fake.
- **What is kept:** the entire local domain (ticket-state machine, sqlite repo, outbox
  settlement, retry/backoff) is implemented and tested, so re-enabling later is a wiring
  change, not a rewrite.
- **Better alternative:** run the task immediately as a normal session; or use
  **Automations** (local cron scheduler, `native/crates/zcode-services-automation`) to run
  work at a chosen time on the user's own machine. Automations need no zcode connection.

### 3.2 Remote content/config (client config, client scenes, rollout flags)

- **Why not built:** they are pure zcode content/feature-flag reads. With the policy they
  would return nothing anyway; shipping a fetch would be a connection we promised not to
  make.
- **Better alternative:** bundled/local defaults (already the behaviour), plus the user's
  own settings, plugins, skills and MCP servers, which are read from local files.

### 3.3 Dynamic workflow engine — ported to Rust (no longer disabled)

- The engine/journal/run service/driver/tools/v4 reads+commands, the live `workflowRuns`
  projection and the cold rebuild are Rust (`specs/workflow-capability-boundary.md`,
  RUST-PORT-LOG ENTRY 139–150). The TypeScript compiler front-end is reused through the
  compile kernel by design; Node remains the sandbox runtime.
- The TS workflow stack is restored and remains the **live path** until the native host is
  the default (removal gate: a flag-gated replacement is not enough). The rollout answer is
  `onDemand` with `ZCODE_DYNAMIC_WORKFLOW_MODE` as override.

### 3.4 Remote plugin marketplace catalog (official CDN partition)

- **Why not built:** the official marketplace catalog is refreshed from a remote source.
- **What is kept:** every marketplace the user adds themselves (local path, git, zip) and
  the bundled official catalog work locally. Only the remote CDN refresh is not fetched.

### 3.5 CUA

- **Why not built:** the upstream TS package is itself a fail-closed placeholder; there is
  no real capability to port.
- **Alternative:** none needed until a real CUA product exists; the boundary is documented
  and the channels answer explicit failures.

### 3.6 Subagent delegation — built, but foreground and one agent type only

- **What is built (2026-10-29):** the `Task` tool really runs a subagent. It opens a child
  session (`taskType: subagent_child`, `parentSessionId` recorded), runs a full turn in it
  with the parent's model and the parent's tool set minus `Task` (recursion is impossible by
  construction), returns the child's final message as the tool result, records the run in a
  per-session registry and in the child's own `subagent-run.json`, and answers
  `session/subagents` from both sources, so ended runs are still listed after a restart.
  `specs/rust-backend-replacement.md` §4.5 tracks it; the behaviour is pinned by
  `native/crates/zcode-host/tests/protocol_methods_e2e.rs::task_tool_runs_a_child_session_and_lists_it_as_an_ended_subagent`.
- **What is deliberately not built, and why:**
  - **Background subagents** (`run_in_background: true`): implemented (the old bullet here was
    stale) — the parent background registry records a `local_agent` task, `TaskOutput` reads
    `subagent-output.txt`, `TaskStop` sets the child cancel bit, and completion posts the
    one-per-task notification. There is no `agent_background_unavailable` refusal.
  - **Named agent profiles**: **ported 2026-10-31** (ENTRY 160). Built-ins
    `general-purpose` + read-only `Explore`, plus `<data-dir>/agents/*.md` (user) and
    `<workspace>/.zcode/agents/*.md` (project, same name overrides). Supported frontmatter:
    `name`/`description`/`model`/`thoughtLevel`/`tools`/`disallowedTools`/`injectAgentsMd`/
    `maxTurns`; `color` is accepted but has no native consumer. `permissionMode`/`memory`/
    `skills`/`mcpServers`/`background` are **rejected with a named
    `agent_unsupported_frontmatter` diagnostic** instead of silently running a weaker agent;
    a model outside the static `--provider-config` catalog is `agent_unknown_model`. Unknown
    `subagent_type` still fails with `agent_unknown_type` and now lists the available names.
  - **Permission re-asking inside the child.** The child has no interactive client, so
    non-read-only tools run under the grant the parent already gave to the `Task` call
    (`full_access` for that child session only). Silently _denying_ would make the subagent
    useless; silently _asking_ would open an interaction nobody can answer. The decision is
    recorded in `native/crates/zcode-host/src/subagent.rs` and in the crate README.
- **Better alternative for the user today:** the parent agent does the work itself in one
  loop (its tool set covers read/search/write/bash/web), or the work is split across
  sessions the user opens. Nothing depends on the missing background mode.

### 4.2.1 Plan mode — ported 2026-10-29

`EnterPlanMode` / `ExitPlanMode` and `v4/conversation/plans` are wired in the native host,
so they are no longer catalog entries. What the user gets:

- a session mode whose permission gate denies every non-read-only, non-destructive-exempt
  tool (including under full access, which is why the gate is ordered before it),
- a plan-approval interaction that is a `userInput` (approve option plus free-text
  feedback), never a generic permission prompt, and never auto-approved when nobody is
  subscribed to answer,
- the approved plan written to `<workspace>/.zcode/plans/plan-<session>.md` before the mode
  restores, and
- a `v4/conversation/plans` directory computed from the authoritative row window, so the
  composer and the plan side-pane survive the tail-window truncation and row edit/retry.

Contract with TS citations: `specs/rust-native-crates.md` S3 "Plan mode" and
"the `v4/conversation/plans` read model". Honest representation differences
(`planEnabled` vs `collaboration_mode == "plan"`, the unused `allowedInPlanMode`
capability bit, swallowed plan-file write failure) are listed in
`native/crates/zcode-host/README.md` item 12a.

Verification: `native/crates/zcode-host/tests/plan_mode_e2e.rs` (four e2e scenarios against
the stdio host with a scripted provider: deny-while-planning → approve → mode restored +
file on disk + directory entry; approval payload shape + feedback is not approval; headless
decline; `ExitPlanMode` outside plan mode), plus the `plan.rs` unit tests for the answer
closure, the sanitize rule, input validation and the gate ordering.

| Bash interpreter selection                                             | The auto-detection branch was ported on 2026-10-30 (`zcode-host/src/shell.rs`, in the same order as TS `bash-shell-provider.ts`: Windows fixed Git path → derive `bash.exe` from `git` → fall back to `cmd /D /C`; Unix `$SHELL` → PATH/PATHEXT → fixed directories → `sh -c`; including the `GIT_EDITOR=true`/`SHELL` overlay). **Two upstream TS inputs are not ported:** (1) the `user-config` override (the user names a shell in the desktop preferences — the override branch of TS `resolveEffectiveWindowsBashShellSelection`); (2) the shell snapshot (`resolveShellSnapshotSelection`, the selection frozen when the session is established). The seam in this host still does not pass either of these into the provider/session configuration (same root cause as the §provider-config gap), so only auto-detection runs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | A user who manually picked CMD/zsh in the desktop gets the auto-detection result (Git Bash on Windows) after switching to the native host, not the one they chose.                                                                                             |
| AskUserQuestion auto-resolution countdown                              | The countdown state machine is wired (`hiddenGrace` 60s → `visibleCountdown` → at 300s it closes with an **explicit empty answer**; snooze is permanent for that interaction; see `specs/rust-native-crates.md` S3). **Two points are not ported:** (1) TS persists the interaction registration and the countdown (`initialAutoResolution` / `parsePersistedAutoResolution`), so the same question keeps counting after a CLI restart; this host's registration table is in-process and a restart does not restore interactions awaiting an answer. (2) the workspace-level toggle `setAskUserQuestionAutoResolutionEnabled` (when off it does not time and collapses in-flight countdowns to snoozed) has no corresponding command in this host, so the eligibility bit is always TS's default true.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | After a restart, a question nobody has answered disappears together with the turn instead of staying pending with its countdown; the user has no toggle to switch auto-ending off globally.                                                                                                           |

## 5. Enforcement and verification

- `node native/tools/check-channel-coverage.mjs` — every registered channel member has real
  dispatch evidence; every removed member cites a spec in `CHANNEL_BOUNDARY` /
  `MEMBER_BOUNDARY`. It fails if a removal lacks a citation or a name is both dispatched and
  removed.
- The same tool also enforces the **v4 method-surface boundary** (`V4_METHODS_UNIMPLEMENTED`
  in `native/crates/zcode-host/src/rpc.rs`, i.e. the table in §4.2): every "unimplemented"
  reason must cite a governance document that **exists** (`specs/*.md` or a crate
  `README.md`), and the method name must still appear in `V4_METHODS` in
  `packages/shared/src/zcode-protocol-v4/transport.ts` — a ghost entry that TS has already
  removed while Rust still carries a reason for not porting it is just as much a stale
  catalog. `--self-test` proves with 6 positive and negative examples that these checks
  really do fail (a gate that no counter-example can trigger is only decoration).
- `native/crates/zcode-services-offpeak/src/disabled.rs` tests pin the disabled answers.
- `native/crates/zcode-services-client/tests/client_channels_local.rs` proves both client
  channels answer from local state through the real registry (no HTTP server involved).
- `native/crates/zcode-services-provider/src/runtime_config.rs` tests pin the local
  workflow/off-peak/force-update answers and the named purchase error.
- `native/crates/zcode-host/tests/protocol_methods_e2e.rs` pins the debug ledger, the
  subagent directory (real child session, real transcript), the goal actions, manual
  compaction's busy guard, generateText's real model call and its cancellation.
- `native/crates/zcode-host/tests/local_ttft_e2e.rs` pins that an observed command emits
  monotonic measured stages and that an unobserved command emits nothing at all.
- `native/crates/zcode-provider/tests/executor_stream.rs` pins the attempt trace
  (status, headers, first-content timestamp, retry delay, stall window) the debug/TTFT surfaces
  are built from.
- A repository-wide scan (P-1 gate) rejects `todo!`, `unimplemented!`, `TODO`, `FIXME`,
  mock/fake/stub modules and placeholder handlers.
- The claim boundary itself is tested in `zcode-services-zai` (request allowlist): no
  prompt, file, conversation or telemetry data leaves the device on the claim path.
