# ZCode related function description and third-party component declaration

This statement applies to the source code disclosed in this repository and its built products. The functions, permissions, storage locations and network behaviors of each running form are different, and the default settings of one form cannot be understood as the unified settings of the entire project.

## 1. AI output, execution permissions and automation risks

AI-generated code, commands, explanations, documentation, and suggestions may contain errors, omissions, security flaws, or third-party rights issues. This should be verified in conjunction with actual documentation, command exit status, tool results, and tests; model claims of "completed," "safely processed," or "authorized" do not constitute proof of fact or authorization. Review execution targets, recipients, and impacts before important operations, and retain recoverable backups.

Files, terminals, Git, Agent tools, and external processes can read and write files, start processes, and access the network within the permissions of the operating system account that actually runs them. In the web or remote workspace, operations may occur on the server, SSH host, WSL or container environment, and the execution location cannot be determined solely based on the device where the current page is located. The current shared Agent execution adapter does not provide a default operating system sandbox; the working directory, workspace identity, Git worktree, browser page isolation, and the running context of the Node REPL should not be regarded as system-level isolation guarantees for all tools.

The shared run configuration uses the `build` permission mode by default; when the standalone CLI performs non-interactive tasks through `--prompt`, `yolo` will be used if `--mode` is not specified. Interactive sessions, desktop sessions, resumed tasks, and hosts can use their own configured, saved, or passed-in modes. Whether to confirm one after another is affected by tool declarations, permission rules and operating modes; `yolo` that does not also enable read-only planning constraints will allow ordinary tool operations. Interactive tools and tools that explicitly require confirmation still have their own rules. Model tool approval is not a unified permission switch for the entire application. It cannot be inferred that terminal operations, plug-in processes or update downloads will all go through the same approval process. For details, see [CLI prompt word mode](apps/zcode-cli/packages/cli/src/run.ts#L486) and [Tool permission judgment](apps/zcode-cli/packages/core/src/permission/service.ts#L97).

## 3. Local data, logs and credentials

Data may be stored on desktop devices, browsers, hosts where the CLI is hosted, SSH/WSL environments, and external services. The data directory of the desktop and server can be affected by the running environment and startup configuration, including settings, sessions, attachments, caches, task records, plug-ins and logs; the stand-alone CLI default session database is located in `~/.zcode/cli/db/db.sqlite`. Closing a window, logging out, uninstalling the client, or deleting a workspace should not be understood to have cleared all copies in other environments, independent data directories, backups, and external services.

The default values ​​and entrances for the memory function are different: the default configuration of the standalone CLI enables memory, and the desktop application setting defaults to off. When enabled, saved sessions and persistent memories can be analyzed and reused in subsequent tasks; related extraction or organization can generate additional model requests. Automation plans, running records, and unfinished tasks also have their own persistence locations. Restoring these records does not guarantee that previous external operations will be undone or can be completely replayed.

The shared Agent's model input and output logs are written locally by default in development and production runs, except in the test environment. Logs may contain prompt words, codes, context, tool parameters and model responses; request headers and some image and video data are desensitized, but it cannot be considered that all user text has been desensitized. Production has rotation and clipping by default, explicitly turning on full preservation will change this behavior. The desktop main process, Host, scheduler, web service and remote daemon process also have their own logs and crash records. The upper limit of a single log does not represent a unified retention period for the entire project.

The credential storage mechanism is also different: the CLI shared credential file uses an encryption mechanism, the default key can be derived from the local environment information, and the read logic also accepts clear text records; the credentials of the desktop/Node service also use local encrypted files and configurable or environment-derived keys, not system keychains; Web OAuth credentials can be saved in localStorage. Model configurations, environment variables, plugin/MCP settings, SSH configurations, and remote synchronized data may also contain valid credentials, and these stores should not be viewed uniformly as system keychains, hardware isolation, or "never leave the machine" guarantees.

The embedded browser uses persistent browsing data; explicitly importing the other browser's Cookies and LocalStorage gives it the appropriate logged-in status. Clearing cache and clearing all site data are different operations. Browser records, downloaded files, web page recording products and model logs are not necessarily deleted by the same cleanup entrance. Do not write real keys or tokens to files tracked by version control. Before copying logs, uploading feedback, sharing conversations, or backing up your data directory, you should check the scope of your acceptance and avoid submitting real credentials, original sessions, and private project content to public repositories or issue reports.
